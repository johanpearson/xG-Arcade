# ADR-0082: Round-completion signal computed client-side; leaderboard link via in-memory navigation, not a URL route

- **Status:** Accepted
- **Date:** 2026-08-22
- **Related requirements:** REQ-1210, REQ-204, REQ-205, REQ-206, REQ-1206, REQ-407, REQ-408
- **Related components:** None in `XGArcade.Core`/`XGArcade.Games.*` — this is a frontend-only decision; see "Why no backend/`IGameModule` change" below for why that itself is part of the decision.
- **Related decisions:** ADR-0003 (generic round/game boundary — Core never learns game internals directly; this ADR deliberately never needs to cross that boundary at all, see Context), ADR-0039 (hash-based, hand-rolled client routing — this ADR explicitly does not supersede it; see Decision §2 and "Why this doesn't trigger ADR-0039's follow-up" below), ADR-0043 (per-`GameKey` leaderboard scoping, reused as-is by the new `LeaderboardRoundTarget` shape)

## Context

REQ-1210 asks for a completion animation, generic across every game xG Arcade hosts (xG Grid, xG Path, and any future game), that shows a player's current points for the round they just finished and a link straight to that specific round's leaderboard for that specific game. REQ-1210 deliberately left two implementation questions open, to be settled here:

**1. Where does "round complete" + "current points" get computed?** Neither game's current-round response DTO (`CurrentRoundResponse`, `CurrentPathResponse`) carries an explicit `isComplete`/`roundComplete` field, and neither game exposes a single backend "player's current total for this round" value. But both DTOs already carry everything needed to derive both: `CurrentRoundResponse.cells[].guess` (xG Grid) and `CurrentPathResponse.puzzles[].guess` (xG Path) each already return a `locked: boolean` plus a per-item authoritative points value (`livePoints`/`points`) — exactly the data `GridScreen.tsx`'s pre-existing `totalKnownPoints` and `PathScreen.tsx`'s per-puzzle rendering already consume today, on every fetch of `GET /rounds/current`/`GET /path/current` each screen already makes.

**2. How does a completion screen link to "this round's leaderboard, this game, live-or-closed as appropriate"?** `frontend/src/App.tsx` uses hash-based routing (ADR-0039): a flat `Screen` union with no per-entity URL parameters. `LeaderboardScreen.tsx` and its child `PastRoundsLeaderboard.tsx` already have local state for which game/scope/round is selected (`gameKey`, `scope`, `selectedRound`), but nothing today can seed that state from outside — every existing entry point (the header nav's "Leaderboard" link) always lands on the same 'all-time'/xG Grid default. ADR-0039's own "Follow-up" section names exactly this shape of need ("a per-round or per-league detail URL") as the trigger to introduce `react-router` and a URL-parameterized route, superseding that decision.

## Decision

**1. Compute completion and current-points entirely client-side, from data already fetched — no backend change, no `IGameModule` extension.**

A new shared module, `frontend/src/lib/roundCompletion.ts`, defines one generic shape:

```ts
interface CompletableItem { locked: boolean; points: number | null }
function computeRoundCompletion(items: readonly CompletableItem[]): { isComplete: boolean; currentPoints: number }
```

`isComplete` is true only once every item is locked; `currentPoints` sums whatever point values are already known (an unknown/null value contributes 0, mirroring how each screen already treated "not yet known" before this change). Each screen owns its own small mapping function (`GridScreen.tsx`'s `toCompletableItem`, `PathScreen.tsx`'s `toCompletableItem`) translating its game's own scoring shape into this generic one — `roundCompletion.ts` itself never branches on which game it's serving. This keeps the signal genuinely generic (ADR-0003's spirit: no game-specific branching lives in a cross-game piece of code) without needing to cross the ADR-0003 boundary at all, because nothing here touches `Core` or `IGameModule` in the first place.

A companion hook, `useCompletionTransition(isComplete: boolean | null): boolean`, fires `true` only on an in-session `false → true` transition, never on a component's first-ever observed value (even when that first value is already `true`) — the deliberate, conservative answer to REQ-1210 §7's explicitly open "replay on revisit?" question: showing the banner only on the actual moment of completing, never automatically on reloading or re-navigating to an already-finished round, requires no new persisted per-player-per-round state.

**Why no backend/`IGameModule` change:** the values needed are already correct and already in flight to the client on every request either screen already makes. Adding a backend field or `IGameModule` method would introduce a second place these values are computed, with no reduction in what the frontend needs to know (it must still map each game's own scoring shape into whatever generic shape a backend endpoint returned) — pure duplication for no behavioral gain, and against this project's own "reuses existing scoring, introduces no new formula" requirement (REQ-1210).

**2. The leaderboard link is in-memory navigation state threaded through the existing screen-switch mechanism — not a URL route.**

`LeaderboardScreen` gains three optional props — `initialGameKey`, `initialScope`, `initialRoundId` — read once via `useState`'s lazy initializer at mount, seeded by `App.tsx`'s new `leaderboardInitial` state and a new `handleViewRoundLeaderboard(target: LeaderboardRoundTarget)` function that sets that state and calls the existing `navigateTo('leaderboard')`. `PastRoundsLeaderboard` gains a matching `initialRoundId` prop, consumed exactly once (ref-guarded) to jump straight into a round's detail view, bypassing the closed-round list — the same underlying `fetchClosedRoundLeaderboard(roundId)` call `handleSelectRound` already made from a list click, just triggered a different way. None of this adds a route, a URL parameter, or a new dependency; the browser hash still only ever encodes `Screen`, exactly as before.

`GridScreen`/`PathScreen` decide `'live'` vs `'past'` by re-asking the same `GET /rounds/current`/`GET /path/current` endpoint they already call on mount, at the moment "View leaderboard" is activated: if that round is still the one currently returned as active, scope is `'live'` (REQ-407, no `roundId` needed — a game has exactly one active round at a time); otherwise (including on a fetch failure) scope falls through to `'past'` (REQ-408, pre-drilled via `initialRoundId`) — see Consequences for the narrow race this doesn't fully close.

**Why this doesn't trigger ADR-0039's "add react-router" follow-up:** that follow-up is specifically about `Screen` growing a nested or parameterized *URL* — back/forward support, a bookmarkable/shareable deep link, a route the server or a shared link needs to resolve. Nothing here does that: `leaderboardInitial` is exactly the same category of thing `PastRoundsLeaderboard`'s pre-existing `selectedRound` state already was (in-memory, component-local, forgotten on reload) — this ADR only makes it seedable from outside the component instead of only reachable by clicking a list row. A page reload while the completion-linked leaderboard view is open lands back on `#/leaderboard` at its default 'all-time' scope, same as every other piece of non-`Screen` UI state in this app already does today (which cell was open, which scope tab was selected, whether the scoring explainer was showing) — not a new gap this decision introduces.

## Alternatives considered

| Option | Pros | Cons | Why not chosen |
|---|---|---|---|
| Add a backend field (e.g. `CurrentRoundResponse.isComplete`/`currentPoints`) computed via a new `IGameModule` method | Single source of truth "on paper"; matches how other cross-game data already flows through `IGameModule` | Pure duplication — the frontend already receives every input needed and must still map each game's own shape into whatever the backend returned; crosses the ADR-0003 boundary for no behavioral gain; adds a second place to keep two scoring paths in sync (violates REQ-1210's explicit "no new scoring path" constraint) | Not chosen: no problem it actually solves, real maintenance cost |
| Supersede ADR-0039, add `react-router`, encode round+game in the URL (e.g. `#/leaderboard/xg-grid/past/<roundId>`) | A "proper," bookmarkable/shareable deep link; resolves ADR-0039's own named follow-up trigger head-on | Pays for browser-history and URL-parsing machinery this one feature doesn't need (REQ-1210 never asks for a shareable/reload-durable link, only "immediately see how I compare"); a genuinely larger, riskier change than this feature's actual scope; ADR-0039's own stated risk profile (SPA-fallback behavior unverified against the real deployed Azure Static Web App) becomes live risk for the first time | Not chosen now: real infra risk and scope, for a capability (bookmark/reload durability of one specific view) nothing in REQ-1210 asked for; still available later if a future requirement genuinely needs it |
| Persist a `RoundCompletionSeen` (or similar) flag server-side, to resolve REQ-1210 §7's "replay on revisit" question definitively | Removes the ambiguity entirely, correct in every session/device | REQ-1210 §7 leaves this an explicitly open product question, not a technical one — building persisted state to answer a question nobody has actually decided yet risks getting the semantics wrong and needing to unwind it; the in-session-transition-only default needs zero new state and is trivially safe (never shows the animation when it shouldn't, at worst doesn't replay when a product owner later decides it should) | Not chosen: premature to build persistence for an unresolved product question; the conservative default costs nothing to build and nothing to undo later |

## Consequences

- Positive: zero backend change — no migration, no new endpoint, no `IGameModule` surface area, nothing crossing the ADR-0003 boundary; the entire feature is reviewable as a frontend-only diff.
- Positive: reuses ADR-0039's existing routing mechanism completely as-is; no new frontend dependency (`frontend/package.json` unchanged).
- Positive: the shared `computeRoundCompletion`/`useCompletionTransition` pair is genuinely game-agnostic — a third game only needs its own `toCompletableItem`-style mapping function, never a change to `lib/roundCompletion.ts` itself.
- Negative / trade-off accepted: the live-vs-past scope check has a narrow race — if a round closes in the exact window between "View leaderboard" being clicked and its confirmation fetch resolving, the player could still momentarily be routed to a 'live' view for a round that closed a moment earlier. Judged acceptable: `LiveLeaderboard`'s own existing polling/refresh behavior for a just-closed round already handles this gracefully (it doesn't crash or show wrong data, REQ-407's own scope), and the alternative (always guessing 'past') would incorrectly 404/409 the far more common case of an actually-still-active round.
- Negative / trade-off accepted: navigating to a round+game-scoped leaderboard this way is not bookmarkable, shareable, or reload-durable — a reload while that view is open returns to the plain 'all-time' default. Accepted because REQ-1210 never asked for that, and because building it now would mean superseding ADR-0039 for a capability nothing currently needs (see Alternatives above).
- Follow-up: if a future requirement explicitly needs a shareable/reload-durable per-round leaderboard link (or browser back/forward more generally), that is the trigger to revisit ADR-0039 itself, per its own already-stated follow-up condition — this ADR does not consume or resolve that trigger, it just declines to pull it forward for this feature.
- Follow-up: REQ-1210 §7's "replay on every revisit vs. only once ever" question remains a genuinely open product decision — `useCompletionTransition`'s in-session-only behavior is this ADR's conservative default, not a resolution of that question.

## For AI agents

Do NOT add a backend endpoint, DTO field, or `IGameModule` method to compute round completion or current-round points for this feature — the client-side computation in `frontend/src/lib/roundCompletion.ts`, fed by data both games' existing current-round responses already return, is the deliberate, complete answer; adding a server-side equivalent would create a second, redundant scoring path this ADR and REQ-1210 both explicitly reject. Do NOT add a URL parameter, route, or `react-router` dependency to carry the round-completion leaderboard link — that would silently supersede ADR-0039 without going through its own stated revisit trigger; use `LeaderboardScreen`'s `initial*` props / `App.tsx`'s `leaderboardInitial` state instead, the same pattern already established here. Do NOT persist any new "has this player seen the completion animation for this round" state to resolve REQ-1210 §7's open replay question on your own initiative — that is a product decision waiting on the product owner, not an engineering one to pre-empt.
